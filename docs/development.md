# Local development and verification

## Required local profile

The selected native evidence profile is macOS on Apple Silicon (`Darwin/arm64`).
The canonical command rejects other OS and architecture combinations; this
describes the profile that was exercised, not compatibility or qualification
for other targets.

Provide:

- C17 and Apple Clang from the macOS Command Line Tools or Xcode.
- The macOS SDK and Apple's `xcrun`, `sw_vers`, and `xcode-select` tools.
- CMake 3.25 or newer, including CTest.
- Git, for the source and exact dependency identities.
- Network access to the public `szTheory/nesturbator` Git repository on the
  first configure when the pinned source is not already in the build tree.
- Network access to the public `szTheory/muhtari` Git repository on the
  canonical opt-in configure when the pinned source is not already in the
  build tree. Muhtari remains off in a normal default build.

## Canonical command

From the checkout root, run:

```sh
./scripts/check.sh
```

The command configures a Debug arm64 build with the compiler and SDK selected
by `xcrun`, explicitly opts the canonical proof into the pinned public
Muhtari source, builds the required CMake targets, runs the required CTests,
and builds separate public C consumers from the installed packages. It also
starts a fresh configure with the Muhtari option omitted, installs the base
SDK, and proves a separate unsanitized consumer works without Muhtari targets,
artifacts or link requirements. A separate enabled configure verifies that a
nonempty `FETCHCONTENT_SOURCE_DIR_MUHTARI` override is rejected by the intended
source-acquisition gate.

The relocated consumer exercises Nesturbator save/restart and the selected
Muhtari session, including refusal continuation, indexed video and audio. The
source checkout, build tree, and original staging path are unavailable during
the relocated consumer's configure, build, and run stages. The installed
package resolves declared cores from its colocated package directories, even
when the consumer supplies conflicting package paths or redirects, and rejects
same-named imported core targets whose archives point elsewhere. The
installed libfuturo archive has no sanitizer runtime requirement; in-tree
checks use private instrumented builds, and the relocated Muhtari session
consumer compiles its own C17 sources with AddressSanitizer and UBSan. The
owned fixture is generated by project code; no commercial media, upstream
test suite, or campaign is run.

## Browser-host package route

The browser package has a separate Linux/amd64 Emscripten and pinned
Chrome-for-Testing route. From a clean checkout, run
[`./scripts/check-browser-package.sh`](../scripts/check-browser-package.sh)
with Docker and public network access. Its seven-scenario inventory, exact
qualified profile and fixture, generated report paths, and browser-specific
limits are in the [browser-host guide](browser-host.md). This does not replace
the native macOS command above or extend its target qualification.

## Optional Apple Clang static analysis

An opt-in advisory driver can replay first-party compile settings from one or
more CMake `compile_commands.json` files:

```sh
python3 scripts/analyze_compile_commands.py \
  /path/to/sdk-build/compile_commands.json \
  /path/to/native-host-build/compile_commands.json
```

The build directories must have been configured from this checkout and retain
their adjacent `CMakeCache.txt`. The driver uses the compiler recorded in each
command, verifies that it is Apple Clang, and preserves distinct compile
configurations. It skips sources outside the checkout and sources inside the
CMake build trees, which excludes build-tree dependencies and generated files.
It reports diagnostic output, the number of analyzed commands and unique
sources, and total wall time. Analyzer findings are advisory and do not fail
the command; unreadable databases and failed analysis invocations do.

This scan is separate from `./scripts/check.sh` and is not part of hosted CI.
It complements compiler warnings and runtime tests; it does not execute the
program, prove a finding is reachable, or qualify other platform/toolchain
configurations. Review each diagnostic against the surrounding code.

After CTest, the canonical command runs the required relocated installed
consumer routes `installed_consumer_save_restart`,
`installed_consumer_load_refusal`, `installed_muhtari_session`, and
`installed_macos_host` and records them as distinct results. The host route
also runs its own fresh CTest inventory from a relocated prefix and records
native-process status and sanitized artifact evidence. The combined Muhtari proof uses one installed
session executable for its normal session, refusal, frame-boundary and oracle
controls. The independent `muhtari_example` smoke route uses the same owned
fixture emitter from the in-tree Muhtari session target. `muhtari_package_modes`
uses fresh scratch configure/install directories and records both route
durations in the CTest output. The canonical inventory checks the required
test and target names against `scripts/check.sh`; each required result must be
registered, enabled, executed and carry its expected evidence. Missing,
failed, skipped, cancelled or evidence-free required results fail the command.
Advisory and unsupported results remain separate; the hosted current-profile
row remains unsupported.

## Identity and result files

The canonical command writes these files under `build/check/`:

- `verification-identity.txt` — line-oriented identity record containing the
  full libfuturo source commit and clean/dirty worktree state; Nesturbator's
  public origin and exact commit; Debug, enforced consumer C17, test/consumer
  sanitizer and `Darwin/arm64` settings; compiler, CMake, CTest, SDK, and OS
  versions; generated fixture identity; sorted relative installed-file SHA-256
  digests; the installed consumer executable digest; and required-result
  references and outcomes.
- `required-results.tsv` — one applicability, outcome, and detail row per
  canonical route result, with registration, execution, proof, and
  result-reference fields.
- `ctest-inventory.json` — fresh CTest JSON-v1 registration inventory.
- `ctest-results.junit.xml`, `ctest-output.log`, and
  `ctest-process-facts.txt` — CTest results, human-readable output, and parent
  process exit/signal facts. JUnit is not used alone to classify cancellation.
- `relocation-reports/` — consumer-owned report with package-resolution paths,
  per-stage path-isolation results, generated fixture digest and provenance,
  exact installed package and consumer executable hashes, the selected
  Muhtari source and fixture identity, and refusal/boundary/oracle child
  outcomes tied to the same installed executable. The macOS-host report has a
  separate relocated-prefix identity and refers to sanitized CTest inventory,
  JUnit, log, process facts, package resolution, and executable/archive hashes.
- `instrumentation-scope.txt` — actual per-translation-unit sanitizer and
  frame-pointer evidence, including the exact pinned core/CPU and consumer
  units; normal installed archives remain sanitizer-runtime-free.

All paths in the identity and consumer reports are relative. Digests identify
the exact bytes tested; they do not prove authenticity or bit-for-bit
reproducibility. The generated MMC1 fixture is project-authored test data, and
its save expectations are maintained separately as literal oracle data.

The identity records elapsed configure, required build, CTest, corpus,
allocation, control, instrumentation, relocation, and installed load-child
time for each run. Focused route timings and the default-off package/example
costs appear in `ctest-output.log`. Refer to any timing with the associated
`run_id`; these are local observed costs, not a performance guarantee.

## Evidence limits

For the optional interactive AppKit launch, mapped controls, display behavior,
and current Phase 7 limits, see the [native macOS host guide](native-macos-host.md).

The current run establishes the selected local macOS arm64 profile and the
exact pinned Nesturbator and Muhtari sources through public consumers. The
Phase 5 Muhtari fixture is a project-authored Apache-2.0 generator output;
its byte count, digest and provenance are checked before the public example
runs. Phase 5 also records a separate owned MIT battery diagnostic reference
for Phase 6 only: source commit
`4642ded6d026f456acf798a43efb081b76987018`, manifest SHA-256
`10f5bc279d8147b3348e102ca9f7e4dc496dd31b5099adb2ef64320e987fb4d4`. That
reference has not been run here and provides no joystick-response evidence.
The earlier hosted dispatch covered a Phase 1 source candidate and is
historical native-only evidence, not a result for the current source or browser
route. The current workflow configuration and hosted evidence are recorded in
[CI activation](ci-activation.md).

This native evidence does not qualify other operating systems or architectures,
browser play (see the separate [browser-host qualification](browser-host.md)),
hardware accuracy, a clean-machine sandbox, broad title or board compatibility,
or crash isolation. Nesturbator and Muhtari remain trusted
in-process cores. Muhtari's selected finite refusal and output boundaries do
not establish general parser safety; its source exposes no native tick getter,
and no battery recovery is demonstrated by this phase. `CORE-03` remains
limited to the accepted finite Nesturbator exact-pin parser partition and
load-preservation scope; exhaustive parser-input safety remains unqualified.
Software release `0.1.0` remains unpublished.
